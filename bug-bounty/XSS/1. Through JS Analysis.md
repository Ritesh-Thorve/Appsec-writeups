# Finding: Reflected Cross-Site Scripting (XSS) via Hidden Endpoint Discovered Through JavaScript Analysis

## Vulnerability Class

Reflected Cross-Site Scripting (XSS)

## Summary

While manually reviewing the application's client-side JavaScript bundles, an undocumented/hidden endpoint was identified that was not linked from any visible part of the UI or referenced in standard application flows. Testing this endpoint revealed that a request parameter was reflected directly into the HTML response without proper output encoding or sanitization.

Submitting a crafted payload in the vulnerable parameter resulted in arbitrary JavaScript execution in the context of the application's origin, confirmed using the following payload:

```
<img src=e onerror=alert(document.domain)>
```

The payload executed successfully, popping an alert box displaying the application's domain, confirming that attacker-controlled script runs in the victim's browser session under the target's origin.

## Impact

- Arbitrary JavaScript execution in the context of the vulnerable application, enabling actions such as session/cookie theft (where cookies are not otherwise protected), credential harvesting via injected fake login forms, or performing actions on behalf of the victim.
- Because the endpoint was undocumented and not exposed through normal navigation, it may not have been covered by prior security testing or automated scanning, allowing the flaw to persist unnoticed.
- Any user who can be induced to visit a crafted link containing the payload is at risk, making this exploitable via phishing or malicious link distribution even though it requires user interaction (reflected, not stored).

## Methodology

1. Reviewed the application's client-side JavaScript bundles (retrieved via the browser's network tab and beautified/deobfuscated for readability) to map out API routes and endpoints referenced in code but not surfaced in the visible UI.
2. Identified a hidden/undocumented endpoint referenced in the JS source that was not reachable through normal navigation or linked pages.
3. Manually explored the endpoint's parameters and observed that one parameter's value was being reflected back into the page's HTML output.
4. Tested basic reflection with a benign marker string to confirm the value was placed directly into the response without encoding.
5. Escalated to a working proof-of-concept payload (`<img src=e onerror=alert(document.domain)>`), which triggered JavaScript execution in the browser upon rendering the response, confirmed via a JavaScript alert displaying `document.domain`.
6. Captured the full request/response and browser execution as evidence, and verified the issue was reproducible across fresh, unauthenticated sessions.

## Root Cause

The vulnerable endpoint reflects a user-supplied parameter directly into the HTML response without output encoding or context-aware sanitization, allowing HTML/JavaScript injection. The fact that the endpoint was undocumented and only discoverable through JS source analysis suggests it was likely excluded from standard security review or automated scanning coverage.

## Recommended Remediation

- Apply proper context-aware output encoding (HTML entity encoding at minimum) to all user-supplied input reflected into HTML responses.
- Implement and enforce a strict Content Security Policy (CSP) to reduce the impact of any XSS that may still occur.
- Ensure all endpoints - including those not directly linked from the UI - are included in the application's security testing scope, since client-side JavaScript often reveals routes that manual browsing alone would miss.
- Adopt a template/framework-level auto-escaping mechanism for all dynamic output, rather than relying on manual encoding at each reflection point.

## Program Status

Reported through the program's VDP disclosure process. Target name, domain, and other identifying details have been withheld in accordance with program policy.
