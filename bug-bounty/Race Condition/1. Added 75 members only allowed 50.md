# Finding: Race Condition Leading to Business Logic Bypass (Organization Member Limit)

## Vulnerability Class

Race Condition / Business Logic Flaw

## Summary

The target application enforces a limit of 50 members per organization for accounts on the free (non-subscription) tier. This limit is intended to serve as a monetization boundary, requiring an upgrade to a paid subscription once the threshold is reached.

By sending multiple concurrent "add member" requests using Burp Suite's Repeater (grouped requests sent in parallel), the server-side limit check could be bypassed. Because the membership count validation and the member insertion were not handled atomically, several requests passed the "under limit" check simultaneously before any of them had incremented the stored count. This allowed the organization to exceed the intended cap.

## Impact

- Circumvention of a core monetization/business control, allowing free-tier accounts to obtain functionality reserved for paid subscriptions.
- Potential for abuse at scale if automated, allowing unlimited organization growth without payment.
- Demonstrates a broader class of race condition risk in the application's limit-enforcement logic, which may affect other quota- or limit-based controls (e.g., seats, API calls, storage) if the same non-atomic check-then-act pattern is used elsewhere.

## Methodology

1. Identified the "add member to organization" endpoint and confirmed the application enforces a hard limit of 50 members on non-subscription accounts through normal, sequential usage.
2. Reached the limit legitimately (50 members) to establish a baseline and confirm the block on the 51st sequential request.
3. Reset the organization to a state just under the limit, then crafted the "add member" request in Burp Suite.
4. Used Burp Suite's Repeater group/parallel send feature to fire a batch of add-member requests simultaneously, rather than sequentially.
5. Observed that the concurrent requests each passed the limit check before the member count was updated, resulting in the organization successfully exceeding 50 members - ultimately reaching 75.
6. Verified the result by checking the organization's member list and count via the application UI and API response, confirming the bypass was persistent and not a rendering artifact.

## Root Cause

The membership limit check (read current count, compare to cap) and the membership insertion (write new member, increment count) were not executed as a single atomic operation. This check-then-act pattern is vulnerable to race conditions when multiple requests are processed in parallel, as each request can read the same "under limit" state before any write is committed.

## Recommended Remediation

- Enforce the member limit atomically at the database level, using row-level locking, unique constraints, or a transactional check-and-increment operation rather than a separate read-then-write sequence.
- Alternatively, use an atomic counter (e.g., a database sequence or atomic increment operation) that rejects the insert outright if the resulting count would exceed the cap.
- Add server-side rate limiting or request throttling on membership-modification endpoints as a defense-in-depth measure.
