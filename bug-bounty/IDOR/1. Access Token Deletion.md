# Finding: Insecure Direct Object Reference (IDOR) - Cross-Organization Access Token Deletion

## Vulnerability Class

Insecure Direct Object Reference (IDOR) / Broken Access Control

## Summary

The application's "delete access token" endpoint does not verify that the access token being deleted belongs to the requesting user or their organization. By supplying the identifier of an access token belonging to a user in a completely separate, unrelated organization, it was possible to successfully delete that token - despite having no relationship, membership, or permission tied to the victim's account or organization.

The token identifier itself is not sequential or otherwise easily guessable. However, the lack of predictability reduces the ease of exploitation but does not prevent it: the endpoint performs no server-side ownership or authorization check at all, so any valid token identifier obtained through any means (e.g., leakage elsewhere in the application, another vulnerability, log exposure, or referral from another endpoint) can be used to delete a token that does not belong to the requester.

## Impact

- A user can delete another user's access token without being part of their organization and without any authorization relationship to the victim account.
- Deleting a victim's access token can break their active integrations, automated workflows, or third-party connections relying on that token, resulting in a denial-of-service style disruption.
- Demonstrates a missing authorization layer on a sensitive, destructive action (token deletion), independent of identifier guessability - the identifier's unpredictability is not a substitute for a proper server-side ownership check.
- If any other endpoint in the application (or a future vulnerability) exposes token identifiers belonging to other users, this flaw becomes immediately and trivially exploitable at scale.

## Methodology

1. Generated an access token under a test account belonging to Organization A, and identified the corresponding "delete access token" request in Burp Suite.
2. Created a second, unrelated test account belonging to a separate Organization B, with no shared membership, invitation, or relationship to Organization A.
3. Captured the delete-token request issued by Organization B's session, then replaced the token identifier in the request body/path with the token identifier belonging to the Organization A account.
4. Sent the modified request using Organization B's authenticated session and observed a successful deletion response.
5. Confirmed the token belonging to the Organization A account was invalidated/removed, verifying the deletion was genuine and not a false-positive response.
6. Noted that while the token identifier is not sequential or trivially predictable, the endpoint performed no ownership or organization-membership check whatsoever - the request succeeded purely because a valid identifier was supplied, regardless of who it belonged to.

## Root Cause

The delete-token endpoint authorizes the request based solely on the validity of the requester's own session, without validating that the target object (the access token identified in the request) actually belongs to the requesting user or their organization. This is a missing object-level authorization check.

## Recommended Remediation

- Enforce a server-side ownership check on every token-deletion request: verify that the token identifier belongs to the authenticated user or a user within their organization before performing the deletion.
- Apply the same object-level authorization pattern consistently across all endpoints that accept a user-supplied object identifier (tokens, sessions, API keys, etc.), rather than relying on identifier unpredictability as a security control.
- Log and alert on delete attempts targeting objects outside the requester's organization, as this pattern is a strong indicator of exploitation attempts.

Reported through the program's responsible disclosure process. Target name, domain, and other identifying details have been withheld in accordance with program policy.
