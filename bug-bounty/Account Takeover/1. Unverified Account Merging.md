# Finding: Account Pre-Hijacking via Unverified Account Merging

## Vulnerability Class

Account Takeover / Pre-Account Hijacking / Broken Authentication

## Summary

The application allows a new sign-up (e.g., via a social/SSO login, invite, or a second registration flow) to be automatically merged into an existing account that already uses the same email address - without first verifying that the person performing the merge actually owns or controls that email address, and without requiring the existing account holder's confirmation or credentials.

This enables a classic pre-hijacking attack: an attacker who knows or guesses a victim's email address can create or trigger an account/session under that email before or independently of the victim's own verification step, and the application will merge access into the victim's existing account. Once merged, the attacker gains standing access to the victim's account and its data, without ever having proven ownership of the email address.

## Impact

- Full account takeover of any user whose email address is known to the attacker, without needing the victim's password or any interaction from the victim.
- Because the merge happens automatically and silently, a victim may have no visible indication that their account has been compromised until the attacker actively uses the access.
- Particularly severe as a "pre-hijacking" pattern: the attack can be staged in advance (e.g., immediately after learning a target's email, before the target ever logs in through the vulnerable flow), giving the attacker persistent, dormant access that activates whenever the victim's flow triggers the merge.
- Undermines the core trust assumption of email-based identity in the application - that possession of an email address implies verified ownership.

## Methodology

1. Identified that the application supports more than one path to associate an account with a given email (e.g., direct registration plus a secondary flow such as SSO login, invite acceptance, or a linked-account feature).
2. Created a victim account using a test email address through the primary registration flow, simulating a legitimate existing user.
3. Without completing any additional verification, initiated the secondary account flow using the same victim email address from a separate, attacker-controlled session.
4. Observed that the application automatically merged the new session/login into the existing victim account, granting access to the victim account's data and settings from the attacker's session.
5. Confirmed no email verification step (e.g., confirmation link, OTP, or ownership challenge) was required at any point during the merge, and no notification or approval was requested from the original account.
6. Validated the takeover by accessing victim-account-specific data and settings from the attacker session, confirming persistent access rather than a temporary or view-only artifact.

## Root Cause

The account-merging logic trusts email address matching alone as proof of identity/ownership, without requiring cryptographic or out-of-band verification (such as a confirmation email, OTP, or explicit approval from the existing account) before linking a new login method or session to an existing account.

## Recommended Remediation

- Require explicit, verified proof of email ownership (e.g., a confirmation link or one-time code sent to the email address) before merging any new login method or session into an existing account.
- Never merge accounts automatically based solely on an email string match; instead, prompt the user to confirm the merge from within an already-authenticated, verified session.
- Notify the existing account holder whenever a new login method is linked or a merge is attempted, and provide a way to review and revoke unauthorized linkages.
- Apply this verification requirement consistently across every account-creation and account-linking path in the application, since a single unverified path is enough to undermine the security of the whole identity model.
